# AI-Assisted Authorization Review (Local LLM Experiment)

## Goal

Evaluate whether a locally hosted LLM can identify authorization flaws that may be missed by traditional static analysis tools.

This experiment evaluates AI-assisted security review as a complement to traditional security tooling rather than a replacement.

## Tool

* Ollama
* qwen2.5-coder:7b

## Experiment Overview

A deliberately vulnerable password update endpoint was extracted from the API and reviewed using a locally hosted LLM running through Ollama.

The objective was to determine whether the model could identify a Broken Access Control / Broken Object Level Authorization (BOLA) vulnerability that was not detected by traditional static analysis tooling.

### Traditional Security Tooling Used

* Bandit
* Semgrep
* OWASP ZAP
* CodeQL

### AI Review Scope

The model was instructed to focus exclusively on authorization logic and answer the following questions:

* Is authentication required?
* Is the authenticated subject extracted from the token?
* Is the requested username compared to the authenticated subject?
* Is an administrative override explicitly checked?
* Is object-level authorization enforced before the password update occurs?

## Privacy and Governance

This experiment was intentionally designed around a restrictive AI governance model.

### Controls

* No source code sent to external AI providers
* Local execution only
* Human review required for all findings
* AI findings treated as advisory, not authoritative
* No automated enforcement decisions based solely on AI output

## Result

The model successfully identified a Broken Access Control / Broken Object Level Authorization (BOLA) password update flaw that was not detected by Bandit.

Specifically, the model recognized that:

* Authentication was present
* Authorization was not enforced
* The authenticated user was not compared against the target username
* An authenticated user could potentially update another user's password

Human review confirmed the finding and corrected the OWASP classification generated by the model.

## Lessons Learned

### Traditional Scanners Remain Essential

Traditional scanners provide deterministic and repeatable security analysis and remain the foundation of an application security program.

Examples include:

* Bandit
* Semgrep
* CodeQL
* OWASP ZAP

### AI Can Complement Existing Tooling

Local LLMs may provide value when reviewing:

* Authorization logic
* Business logic flaws
* Trust boundary assumptions
* Abuse cases
* Threat modeling scenarios

These areas are often difficult for traditional scanners to detect reliably.

### Human Validation Is Required

AI-generated findings should be reviewed and validated by a security engineer before any remediation or enforcement action is taken.

The model correctly identified the authorization flaw but incorrectly classified the issue under an OWASP category, demonstrating the need for human oversight.

## AI Tool Security Considerations

Local AI models and inference servers should be treated as software assets and incorporated into normal security and governance processes.

### Risks

* Vulnerabilities in AI tooling (e.g., Ollama CVEs)
* Unauthorized access to local inference APIs
* Supply chain risks from model downloads
* Prompt injection and misleading output
* False positives and false negatives
* Overreliance on AI-generated findings

### Mitigations

* Keep Ollama patched and monitor security advisories
* Restrict Ollama access to localhost
* Do not expose inference APIs publicly
* Use trusted model sources
* Require human validation of findings
* Use AI as an advisory control rather than an enforcement control

## Operational Considerations

### Monitoring

* Track vendor security advisories
* Review release notes before upgrades
* Monitor relevant CVE disclosures

### Patch Management

* Update Ollama regularly
* Revalidate functionality after upgrades
* Review model updates before adoption

### Governance

* No source code sent to external AI providers
* Local execution only
* Findings require human validation
* AI-assisted reviews supplement, but do not replace, traditional security tooling

## Conclusion

This experiment demonstrated that a locally hosted LLM can assist in identifying authorization and business-logic vulnerabilities that may be missed by traditional static analysis tools.

The most effective approach is a layered review process:

1. Traditional security tooling for deterministic analysis
2. AI-assisted review for contextual reasoning and business logic assessment
3. Human validation for final security decisions

This approach provides the benefits of AI-assisted security analysis while maintaining strong privacy, governance, and security controls.
